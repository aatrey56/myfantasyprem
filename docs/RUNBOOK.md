## Local stack (app against the real server)

```bash
npm ci
npm run dev:stack   # Postgres (docker compose, db), migrations, demo seed, API on :8080
npm run dev:web     # second terminal: the web app on :8081, API from apps/app/.env.development
```

- Sign in with `demo@myfantasyprem.test` ("Email me a sign-in link"). The
  API terminal prints a `dev magic link` line; open its `link`
  (`http://localhost:8081/sign-in?token=...`) or type its `code`.
- The demo is fictional (internal/demo, generated by `go run
./tools/genworld`): 20 invented clubs, 300 players, "The Sunday Draft"
  with nine teams, gameweeks 1-6 final, gameweek 7 live, gameweek 8 with a
  double and a blank. The other managers' accounts are
  `priya@`, `olu@`, ... `@myfantasyprem.test` (see `demo.Managers`).
- The poller runs on the demo source (`POLLER_SOURCE=demo`): it re-reads
  the embedded files every 30 s and never calls FPL.
- Port 8080 taken? `HTTP_ADDR=:8090 npm run dev:stack` and put
  `EXPO_PUBLIC_API_BASE_URL=http://localhost:8090` in
  `apps/app/.env.development.local` (git-ignored), then
  `npx expo start --web --clear` once from `apps/app`.
- Without Docker: `npm run dev:server` keeps every store in memory and
  seeds the same demo world at start (`SEED_DEMO=true`, the default); data
  is lost on restart. Add `AUTH_DEV_MAGIC_LINKS=true` to sign in.
- Everything works against the server: lineups, waivers, free agents,
  trades, the draft room and live updates over the realtime socket (the
  app opens one per league; `realtime connected` lines in the API log).
  Jobs run in the API process (River on the local Postgres; the tick every
  15 s), so waivers run at each gameweek's waiver deadline in real time.
- More managers: sign in as `priya@myfantasyprem.test` (and the others in
  `demo.Managers`) in a second browser profile, with the magic link the
  API logs. To try a draft, create a league in the app, invite the others
  with its code and start it from the draft room; managers who do not
  pick in time are autopicked when their clock runs out.
- A session without the email round trip: `DATABASE_URL=... npm run admin
-- session -email demo@myfantasyprem.test` prints the session the app
  stores (put it in `localStorage['mfp.session']`).

### Production

Set `APP_ENV=production` on every production instance. The server then
refuses to start (and says why) when `AUTH_DEV_MAGIC_LINKS` is on,
`DATABASE_URL` is missing (no silent memory mode), `REALTIME_URL` or
`APP_URL` is missing, or `CORS_ALLOWED_ORIGINS` is unset or `*`; it also stops
honouring `X-Forwarded-Host`/`X-Forwarded-Proto`. Set `TRUSTED_PROXIES` to
the load balancer's addresses, or every client looks like the balancer to
the rate limits (they are keyed by client IP).

`CLAIM_LINK_SIGNIN=true` is allowed in production for the testing phase
(ADR 0013; `deploy/compose.prod.yml` sets it): the server then logs
`CLAIM_LINK_SIGNIN is on in production` at start. Anyone with a seat's
claim link gets an account and that seat without an email, and that
account cannot add an email yet. Set it to `false` once email, Google or
Apple sign-in works for the testers.

`BRANDED_ASSETS` must be set explicitly in production (`true` or `false`;
the server refuses to start without it). On, `/v1/assets/*` serves the
official club crests, shirts (goalkeeper variant with `?gk=true`) and player
photos: the server maps our ids to FPL's permanent `code` values, fetches
each image once (2 at a time, 4 a second, `FPL_USER_AGENT`, 10s timeout),
keeps it in `ASSETS_CACHE_DIR` and serves it with a week's `Cache-Control`.
A cached image older than 7 days is fetched again in the background (the
cached copy is served meanwhile and kept if upstream fails or no longer has
it), so new headshots and shirts arrive within a week. An image upstream
does not have stays a 404 for a day; failures back off
for 10 minutes and are logged at debug only. Off, those endpoints answer
404 without fetching anything and the app draws its generic shirts. It is on
for the private build (web on Tailscale, dev iOS builds) and **must be off
for App Store and other public builds** (Apple's intellectual-property
guideline); the App Store build also sets `EXPO_PUBLIC_BRANDED_ASSETS=false`
(`apps/app/eas.json`, `production`), which turns the images off in the app
whatever the server says. Default templates (`internal/assets`):

- photos: the newest season first, `https://resources.premierleague.com/premierleague25/photos/players/110x140/{code}.png`,
  then the old archive `.../premierleague/photos/players/110x140/p{code}.png`
  as a last resort (its headshots can be seasons out of date). A new
  season's prefix is one line at the top of `PlayerPhotoSeasons`
  (`internal/assets/proxy.go`, e.g. `premierleague26`);
- crests: `https://resources.premierleague.com/premierleague/badges/70/t{code}.png`,
  then `.../premierleague/badges/t{code}.png`;
- shirts: `https://fantasy.premierleague.com/dist/img/shirts/standard/shirt_{code}-110.png`
  (goalkeeper `shirt_{code}_1-110.png`), then the same under
  `https://draft.premierleague.com/img/shirts/standard/`.

If upstream moves them, override the `ASSETS_*_URLS` templates; clear
`ASSETS_CACHE_DIR` (or wait a day for misses to expire) afterwards.

**Clearing stale player photos now** (photos cached before the
newest-season-first order, e.g. a player in a former club's shirt): stop
the API, delete the cached photos, start it again; each photo is fetched
once more on first view. On the private tailnet host:

```sh
rm -rf ~/mfp-tailnet/assets-cache/player-photo   # only photos; crests/shirts stay
```

The server recreates the directory on start. Without clearing, each stale
photo is replaced within 7 days of its cache date anyway. Browsers and the
app keep their own copy for up to a week (`Cache-Control`); a reload with
cache disabled, or reinstalling the build, shows the new one at once.

**Before App Store submission:** set the four `APPLE_*` token variables
above (Apple Developer > Keys: a key with Sign in with Apple, its key id,
the team id; `openssl rand -base64 32` for `APPLE_TOKEN_KEY`). Without
them the server logs `Apple token revocation is NOT configured` at start
and account deletion cannot revoke Apple tokens (guideline 5.1.1(v)).
Losing or changing `APPLE_TOKEN_KEY` makes stored tokens unreadable.

### Rate limits

In-process token buckets per instance (`httpapi.DefaultRateLimits`):
every request 600/min per IP (burst 200); `/v1/auth/*` together 20/min
per IP (burst 10); `POST /v1/auth/email` also 5 links per email address,
then one per 5 minutes; `POST /v1/auth/email/code` also 5 wrong codes
per emailed sign-in (then it, link included, is dead) and 10 wrong codes
per address per rolling 24 hours (then 429 until the oldest is a day
old; the emailed link still works). The code limits are in Postgres
(`sign_in_code_failures`), not in-process: they hold across instances
and restarts. To unlock an address early, `DELETE FROM
sign_in_code_failures WHERE email = '...'`; `GET /v1/invites/{code}` 20/min per IP (`POST /v1/auth/claim`, the
claim-link sign-in, shares the `/v1/auth/*` limit); invite
accept 20/min per IP and 10/min per user; realtime tickets 60/min per IP
and 20/min per user. Revocations (`POST /v1/auth/logout`, `DELETE
/v1/me`) with a token that authenticates are limited only per session,
60/min (burst 30), and skip every per-IP limit, so others sharing the
client's public IP cannot stop someone revoking their own session; with
a token that does not authenticate they count against the IP limits as
before (each still costs one session lookup). The app signs out locally
at once and retries a logout that fails (429 honouring `Retry-After`,
5xx, offline) for two minutes, then keeps the session as pending
revocation (`mfp.pendingRevocations`) and retries it on the next start.
IPv6 clients are keyed by their /64. Over a limit: 429 `rate-limited`
with `Retry-After`. Each limiter holds at most 100,000 keys: when every
one is still limiting, new keys share one overflow bucket (a throttled
key is never reset to make room). Behind N instances the effective limit
is N times higher.

## Migrations

- SQL files in `server/internal/store/migrations/`, numbered, embedded in
  every binary. Never edit one that has run anywhere shared; add a new file.
- `npm run db:migrate` (or `DATABASE_URL=... go run ./cmd/migrate up`)
  applies pending ones and prints the status; `go run ./cmd/migrate status`
  lists them; `go run ./cmd/migrate down -to 0` empties the database
  (destroys data).
- `cmd/seed` and `cmd/api` with `MIGRATE_ON_START=true` also migrate.

## Seeding

- `DATABASE_URL=... npm run db:seed` (`npm run dev:stack` does it for you)
  migrates, loads the demo world and creates the demo league.
  It is idempotent: a second run refreshes the stats, reuses the league and
  rescores.
- The demo's ids live under provider `demo` in the id maps, so its
  players never merge with real FPL ones. Do not point a seeded database
  at `POLLER_SOURCE=fpl`; reset it first (`docker compose down -v` for the
  local volume).

## Tests against Postgres

- `npm run test:go:db` starts its own throwaway postgres:17 container (tmpfs,
  free host port chosen by Docker, unique name, always removed afterwards), so
  parallel runs in several worktrees do not collide, and runs every Go suite
  with `TEST_DATABASE_URL` and `-timeout 20m`; each test gets a
  fresh database cloned from a migrated template. It is in `.office/checks`.
- Plain `npm run check` skips the Postgres halves (memory only). CI sets
  `TEST_DATABASE_URL` from a Postgres 17 service, so it runs both.

## Poller operations

- Exactly one process runs it (`POLLER_ENABLED=true`). Logs carry
  `component=poller`: `poll ok` (mode, gameweek, next_in), `rescored
leagues`, and `poll failed; keeping the last good snapshot` (err,
  consecutive_failures, last_good_at, stale, retry_in).
- State: `SELECT * FROM poll_state;` shows mode (`live`, `bonus`,
  `unchecked`, `idle`), the gameweek, last attempt and last good poll, the
  next poll and the last error.
- `SELECT * FROM rescore_pending;` lists gameweeks whose stats changed
  but whose rescore has not succeeded yet; the poller retries them in full
  every cycle, also after a restart.
- Host sleep (a laptop server with its lid shut): Go timers stop while the
  host sleeps, so the poller waits for a wall-clock due time in chunks of at
  most a minute and polls within a minute of waking if a poll fell due. A
  `poller: wall clock jumped ahead (host asleep?)` warning marks each
  resume. Waits are also capped at the next kickoff and 30 minutes before
  the next gameweek deadline. Live scores still stop while the host
  sleeps: keep a match-day server awake (`sudo pmset -a disablesleep 1`;
  `caffeinate` does not stop lid-close sleep).
- Metrics: with `METRICS_ADDR`, `curl $METRICS_ADDR/debug/vars | jq .poller`:
  `polls`, `poll_failures`, `invalid_responses`, `players_changed`,
  `leagues_scored`, `teams_changed`, `last_good_unix`,
  `consecutive_failures`, `stale`, `gameweeks_reconciled`,
  `reconcile_failures` (earlier gameweeks re-fetched on start, rollover or
  backfill; failures are retried next cycle), `mode`.
- Games started (`starts`, migration 00019): lines stored before it have
  `starts` NULL. No admin step: on start the poller re-reads every earlier
  gameweek whose lines have minutes but no starts, `BackfillPerTick` (4)
  per cycle at most two requests a second, so after the deploy a 9-gameweek
  season fills within three cycles. Check:
  `SELECT gameweek, count(starts) FROM player_gameweek_stats GROUP BY 1 ORDER BY 1;`
- Raw payloads: `stat_snapshots` keeps each distinct upstream payload
  (bootstrap, live per gameweek). The hourly prune job keeps the newest
  `SNAPSHOTS_KEEP` per kind and gameweek plus every final one (stored after
  the gameweek's data was checked); by hand: `npm run admin --
prune-snapshots -keep 50`.

## How to tell data is stale

- API: every stats-derived response has `meta.stale`, `meta.dataAsOf` and
  `meta.serverTime`. While matches are live, `stale` turns true 3 minutes
  after the last good poll; between matches it turns true when the poller
  is failing or more than 3 minutes past its scheduled poll (stopped).
- Database: `SELECT mode, last_good_at, next_poll_at, consecutive_failures,
last_error FROM poll_state;`.
- Metrics: `poller.stale` is 1 while live data is stale.
- App: the "FPL data delayed since hh:mm" banner.

## FPL API down or blocked

Symptoms: `meta.stale = true` on responses, the app's "FPL data delayed
since hh:mm" banner, poller errors in the logs.

- Confirm: `poll_state.last_error` and the `poll failed` log lines. Does
  `https://draft.premierleague.com/api/game` answer from your laptop and
  from the server? Compare status codes (403/429 means blocked or rate
  limited, 5xx means down). `invalid_responses` rising means FPL answered
  with something we reject (a changed shape): check the newest
  `stat_snapshots` and the client's validation in `provider/fpl`. Real
  Draft payloads (2026-27 gameweek 6) are in
  `provider/fpl/testdata/real-gw6`, replayed by the `Real*` tests in
  `provider/fpl` and `poller`; add a newer capture there when FPL changes
  shape.
- The last good snapshot keeps being served; scores are never zeroed. The
  poller retries with exponential backoff (30 s doubling to 10 min while
  live) and honours `Retry-After`.
- If blocked: check `FPL_USER_AGENT`, point `FPL_BASE_URL` at the fallback
  network route (TODO: which), keep a single poller process.
- Communicate: TODO (status page / in-app notice).

## Stat corrections

FPL can correct points after matches, even a day later.

- The poller re-ingests the current gameweek every poll and daily
  afterwards; a correction changes `player_fixture_stats` (`rev` goes up),
  and the affected leagues are rescored from scratch (`team_gw_scores.rev`
  goes up). Reads always score from the current stats.
- Restarting the poller process forces a full rescore of the current
  gameweek. Any gameweek, by hand: `DATABASE_URL=... npm run admin --
rescore -gw 7` (all in-season leagues; add `-league lg_...` for one). It
  prints the corrections and, like the poller, reports
  `matchups.updated` and `score.corrected` (an official or final team score
  that changed, with the points before and after) to connected clients;
  the API logs each as `score corrected`. A rescore by hand and the
  poller's rescore of the same gameweek take turns (an advisory lock), so
  running one during a poll cannot leave older scores behind.
- Compare against FPL: our per-fixture points must equal FPL's `explain`
  totals (the golden test in `internal/stats`); `stat_snapshots` holds the
  payloads we scored.

## Jobs (River)

Design: [ADR 0010](adr/0010-league-state-and-scheduled-jobs.md).

- What runs: `draft_clock` at each pick deadline, `trade_review` at each
  review window's end (both inserted with the change that set them),
  `tick` every `JOBS_TICK` (drafts due to start, expired clocks, lineup-lock
  announcements, waiver runs at deadline − 24 h, offer expiry, closed
  review windows) and `prune` hourly. The tick is the backstop: a deadline
  is processed within one tick even if its precise job is lost.
- Every job is idempotent; running one twice, late or on two instances
  changes nothing. `JOBS_ENABLED=false` stops an instance from working jobs
  (it still schedules them); keep at least one instance with it on.
- State: `SELECT kind, state, scheduled_at, attempt, errors FROM river_job
ORDER BY id DESC LIMIT 50;`. Failed attempts are retried with backoff;
  `state = 'discarded'` jobs ran out of attempts (look at `errors`). Logs:
  `component=jobs` (`job failed`, with the league) and `component=river`
  (warnings only).
- Run everything due now, by hand: `DATABASE_URL=... npm run admin -- tick`
  (prints what it did).
- River's tables come with `store.Migrate` (`rivermigrate`); `cmd/migrate
down -to 0` removes them too.

## Draft operations

- A league's draft: `SELECT status, starts_at, pick_timer_s, clock_started_at,
paused_at FROM drafts WHERE league_id = '...';` and its picks in
  `draft_picks`. The clock's deadline is `clock_started_at + pick_timer_s`;
  nothing else stores it, so a restart cannot lose it.
- Stuck clock (a team on the clock past its deadline): `npm run admin --
tick` settles it (autopick, autopick on for that team). If it keeps
  failing, `job failed` logs carry the reason (for example no player left
  that the squad can take).
- The commissioner pauses and resumes in the app (`POST
/draft/pause|resume`); resuming restarts the current pick with a full
  clock. A scheduled draft starts by itself once `draft.startsAt` passes and
  every team has a manager.
- Completion creates rosters from the first gameweek whose deadline has
  not passed, default lineups, the H2H schedule (odd team counts play the
  league average) and the waiver order (reverse draft order).

## Previous seasons (player card)

- The player card's "Previous seasons" reads `player_seasons` (FPL
  element-summary `history_past`, keyed by FPL `code`). The hourly
  `fetch_history` job fetches every player once per season (from 1 July)
  and any player seen for the first time, one request at a time (about 6
  minutes for 700 players). `player_history_fetches` says when each code
  was last fetched.
- By hand: `npm run admin -- fetch-history` (new players and a new
  season only) or `npm run admin -- fetch-history -all` (every player).
  `POLLER_SOURCE=demo` reads the demo world instead of FPL.
- A stat FPL did not track in a season is NULL, never 0 (see
  `server/internal/provider/fpl/history.go` for the first seasons).

## Waivers and trades operations

- Where a league stands: `GET /v1/leagues/{id}/waivers` (`nextRunAt`,
  `lastRunAt`, priority) or `SELECT * FROM league_runs WHERE league_id =
'...' ORDER BY gameweek;` (`waivers` and `lineup_lock` rows mark done
  work).
- A missed waiver run (jobs down at the deadline) runs at the next tick.
  To run one by hand: `npm run admin -- run-waivers -league lg_... -gw 9`
  (a second run of the same gameweek does nothing). Results: claims in
  `waiver_claims` (`status`, `failure_reason`), entries in `transactions`.
- Locks: `waiver_locks` lists players added or dropped by a move (dropped:
  on waivers; added: cannot be dropped) until the run of `until_gw`.
- Trades: `SELECT id, status, review_mode, review_ends_at, failure_reason
FROM trades WHERE league_id = '...' ORDER BY created_at DESC;`. Offers
  expire at the next waiver run; review windows close at `review_ends_at`
  (the tick or the `trade_review` job), then the trade processes or is
  vetoed. `failed` with `player_no_longer_on_roster` also marks offers
  cancelled because another trade with the same players was accepted.

## Realtime operations

Design: [docs/realtime.md](realtime.md), [ADR 0011](adr/0011-realtime-websocket.md).

- Logs: `realtime connected` / `realtime disconnected` (conn, user) per
  socket; `realtime render failed` / `realtime publish failed` when an
  event could not be built or stored (clients then catch up by polling);
  `realtime listener reconnecting` when an instance lost its LISTEN
  connection (it retries with backoff; events in that window reach its
  clients only as a `seq` gap, which makes them refetch).
- The log: `SELECT league_id, seq, type, sent_at FROM realtime_events
ORDER BY sent_at DESC LIMIT 20;` (five minutes are kept); the counter is
  `realtime_seq`. Tickets are single use and live 60 s
  (`realtime_tickets`).
- Behind a proxy: allow WebSocket upgrades on `/v1/realtime`, idle
  timeouts above 60 s (the client pings every 25 s), and set
  `REALTIME_URL` if the public host differs from what the API sees.
  `CORS_ALLOWED_ORIGINS` is also the WebSocket origin allow-list.
- Close codes clients may report: 4403 (not, or no longer, a member),
  4401 (session ended: logout, refresh-token reuse, account deletion, or
  the one-hour socket lifetime; it reconnects with a new ticket), 4400
  (bad message), 1013 (fell behind; it reconnects), 1001 (shutdown). The
  app falls back to polling while disconnected.
- Revocations (leave, removal, logout, deletion) reach every instance on
  the `realtime_control` NOTIFY channel; a `realtime revoke failed` log
  means only this instance closed its sockets (the others close theirs
  within the socket lifetime).

## Sign in with Apple and Google

- Set `APPLE_CLIENT_IDS` (the iOS bundle id and the web Services ID) and
  `GOOGLE_CLIENT_IDS` (each OAuth client id: web, iOS, Android). Without
  them those sign-ins answer 503 `sign-in-unavailable`.
- The server fetches the providers' public keys (Apple
  `https://appleid.apple.com/auth/keys`, Google
  `https://www.googleapis.com/oauth2/v3/certs`) and caches them; it keeps
  serving a known key if the fetch fails. A 401 `invalid-identity-token`
  logs `identity token refused` with the reason (audience, issuer, expired,
  signature, nonce); a 503 while the provider is unreachable logs
  `identity provider unreachable`.
- A first sign-in links to an existing account when the provider says the
  email is verified; otherwise it creates a new account.

## Account deletion

- `DELETE /v1/me`: [account-deletion.md](account-deletion.md). Pending
  claims are cancelled and open offers withdrawn or declined, teams are
  orphaned (pre-draft teams deleted), a commissioner's role passes on, and
  the user, sessions, identities and pending magic links are deleted (one
  transaction). Support cannot undo it.
- Apple tokens are revoked at deletion when the `APPLE_*` token variables
  are set (required before App Store submission, see Production above).
  Logs: `apple authorization code exchange failed` at sign-in (that
  account's token cannot be revoked later), `apple token revocation
failed` or `apple token NOT revoked` at deletion.

## App against the real server (Playwright)

- `npm run test:e2e:server` (needs Docker, or `TEST_DATABASE_URL` /
  `DATABASE_URL` pointing at a database it may wipe). It starts its own
  postgres:17 container (unique name, tmpfs, free port on 127.0.0.1) and
  removes it at the end, on failure and on SIGINT/SIGTERM/SIGHUP, so runs
  from several worktrees do not collide. `E2E_API_PORT` (default 8091) and
  `PW_PORT` (default 4174) move the API and the web build for a second run.
  It resets and seeds the database, builds the web app against
  `http://localhost:8091` into a temp dir, starts the API there
  with the poller on demo data, signs in the demo commissioner and runs
  `e2e-server/` (hub, league page with its realtime socket, team, players,
  activity, matchup, draft). Not in `.office/checks`.

## App banners: which one means what

Each screen shows at most one banner, from its own data:

- "You're offline": the device has no connection. Nothing to do server-side.
- "Can't reach the server · showing data from hh:mm": the app's latest
  request to our API failed (5xx, timeout, network). Check API health
  (`/healthz`), logs by `X-Request-ID` (every problem body carries
  `requestId`), and the proxy.
- "FPL data delayed since hh:mm": our API answers but upstream data is older
  than 3 minutes (`meta.stale` or the client's own age check). See "FPL API
  down or blocked".

## League import stuck or failing

The import is deprecated for v1 (ADR 0008); this applies when it returns.

- Imports are jobs (ADR 0007): `GET /v1/imports/{importId}` shows `status`,
  `progress` and `error`.
- A `failed` import does not block a retry; `POST /v1/imports` again.
- 422 `classic-league-url`: the user pasted a fantasy.premierleague.com
  link; they need the draft.premierleague.com one.
- Today the server fakes the job in memory and always ends in `failed`
  ("not implemented").

## Automatic FPL checks (shadow checks)

Until the switch-over, every imported league is compared with FPL Draft
read-only (ADR 0016): nothing in the league changes.

- An hourly River job (`fpl_shadow_plan`) schedules `fpl_shadow_check`
  jobs for the next 36 hours from the FPL calendar: 10 minutes after the
  waiver run, 15 minutes before and 10 after the deadline, and at each
  match's kickoff, +55 min, +115 min and +175 min (bonus), plus once after
  FPL marks a gameweek's data checked. Slots shared by matches run once.
- Each check stores its report (`mirror_shadow_checks`, newest 200 per
  league). The commissioner sees the latest under League settings,
  "Automatic checks"; a mismatch also shows on the league strip and sends
  an `fpl_check_mismatch` notification (once per set of differences).
- Differences while FPL is still updating (live matches, provisional
  bonus) are `pending`; they become `mismatch` only on final data.
- Run one now: `npm run admin -- shadow-check -league lg_...` (prints every
  item that is not ok).
- Stop them: set `FPL_SHADOW_UNTIL` to the switch-over date.
- A failed check is logged (`shadow check failed`) and not retried; the
  next slot checks again.

## Signing in on a dev server

- Production runs with `EMAIL_PROVIDER=none` for now (claim links, and
  `deploy.sh admin session -email ... --i-know` for the commissioner:
  docs/DEPLOY.md "First commissioner login"); with Resend set up it mails
  links (`EMAIL_PROVIDER=resend`; see "Magic-link email not arriving"). Locally, with
  `AUTH_DEV_MAGIC_LINKS=true` (or `EMAIL_PROVIDER=log`) it logs each magic link (`dev magic link` log
  line with `link`, `token` and `code`); open the link, type the code on
  the "Check your inbox" screen, or `POST /v1/auth/email/verify` with the
  token. Never set it in production:
  anyone who can read the logs can sign in as anyone.
- Without `DATABASE_URL`, accounts, sessions and leagues are in memory and
  vanish on restart.
- 401 with `WWW-Authenticate: Bearer`: missing, expired (1 hour) or revoked
  token; refresh with `POST /v1/auth/refresh`. Reusing an old refresh
  token revokes the session by design.

## Mock code in a production build

- `npm run verify:prod-bundle` (CI runs it after `build:web`) fails if
  `apps/app/dist` contains MSW, `mockServiceWorker.js` or mock league data.
- Cause seen before: Metro's cache ignores `EXPO_PUBLIC_*` changes. Both web
  builds pass `--clear`; for a local dev server switching between
  `dev:web` and `dev:web:mocks`, run `npx expo start --clear` once.
- Never deploy `dist-mocks`.

## Roll back a web deploy

- The web app is a single-page app (`npm run build:web:pages`, one
  `index.html` plus hashed bundles, `_headers` and `_redirects`) on
  Cloudflare Pages; the API is at its own origin (`EXPO_PUBLIC_API_BASE_URL`,
  baked in at build time).
- Roll back: Cloudflare dashboard > Workers & Pages > the project >
  Deployments > an earlier production deployment > "Rollback to this
  deployment". Instant; no rebuild.
- The API contract is versioned under `/v1`; a client rollback must stay
  compatible with the running server.
- API rollback: `deploy/deploy.sh rollback` on the VM ([DEPLOY.md](DEPLOY.md)).

## Magic-link email not arriving

- API log: `magic link sent` (with Resend's `email_id`) or `magic link not
sent` (with Resend's status and message). A 403 `domain not verified`
  means the DNS records in Resend > Domains are not verified yet; 429 means
  the rate or the free plan's daily cap (100 a day) was hit.
- Resend dashboard > Emails shows delivery, bounces and spam complaints.
- The link opens `APP_URL/sign-in?token=...`; a wrong `APP_URL` sends people
  to the wrong host (invite links, `APP_URL/join/CODE`, too).
