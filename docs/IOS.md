# iOS

The native app is the same Expo app as the web build (`apps/app`), built
for iOS with Expo prebuild and Xcode. This page covers running it in the
Simulator and on your own iPhone, pointing it at an API, the native tests
and what TestFlight will need later.

Commands run from the repo root unless a step says `apps/app`.

## Prerequisites

- **macOS with Xcode** (26.x is what the tests ran on). Install from the
  App Store, open it once and accept the licence, then
  `sudo xcode-select -s /Applications/Xcode.app`.
- **An iOS Simulator runtime.** Xcode → Settings → Components → iOS
  (any 17.x or newer). Create a phone simulator once:

  ```bash
  xcrun simctl create "MFP iPhone" com.apple.CoreSimulator.SimDeviceType.iPhone-15-Pro \
    com.apple.CoreSimulator.SimRuntime.iOS-17-4   # or a runtime from: xcrun simctl list runtimes
  xcrun simctl boot "MFP iPhone" && open -a Simulator
  ```

- **CocoaPods** (`brew install cocoapods`), used by `expo prebuild`.
- **Maestro** for the native tests (needs Java 17+, e.g.
  `brew install openjdk@17`):

  ```bash
  curl -fsSL "https://get.maestro.mobile.dev" | bash   # installs ~/.maestro/bin/maestro
  ```

  `npm run test:ios` also finds it in `~/.maestro/bin` when it is not on
  `PATH`.

- `npm ci` at the repo root, as for the web app.

`apps/app/ios/` is generated by `npx expo prebuild` and git-ignored. Values
read at prebuild time (bundle id, Sign in with Apple, plain-HTTP hosts)
need `npx expo prebuild --platform ios --clean` from `apps/app` when they
change. `EXPO_PUBLIC_*` values are read when the JavaScript is bundled
(every build), and a Release build embeds that bundle, so it runs without
Metro.

## App identity

| Setting                            | Default                     | Read at  | What it does                                                             |
| ---------------------------------- | --------------------------- | -------- | ------------------------------------------------------------------------ |
| `APP_BUNDLE_ID`                    | `com.myfantasyprem.app.dev` | prebuild | iOS bundle id. The store id is picked when the app is named.             |
| `APP_SCHEME`                       | `myfantasyprem`             | prebuild | `myfantasyprem://...` links open the app.                                |
| `APPLE_SIGN_IN`                    | on                          | prebuild | `false` drops the Sign in with Apple entitlement and button (free team). |
| `APP_LINK_DOMAIN`                  | unset                       | prebuild | Universal links domain. Needs a paid team and the domain's AASA file.    |
| `APP_HTTP_HOSTS`                   | unset                       | prebuild | Hosts the app may reach over plain HTTP (development builds only).       |
| `APP_UPDATES_URL`                  | unset (updates off)         | prebuild | Over-the-air updates manifest URL ([below](#over-the-air-updates)).      |
| `APP_RUNTIME_VERSION`              | native fingerprint          | prebuild | Pins the runtime version updates must match, instead of the fingerprint. |
| `EXPO_PUBLIC_API_BASE_URL`         | none                        | bundle   | The API. Required for any non-mock native build.                         |
| `EXPO_PUBLIC_USE_MOCKS`            | unset                       | bundle   | `true` serves the in-process mock API: no server needed.                 |
| `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` | unset                       | both     | Google sign-in on iOS (the server needs it in `GOOGLE_CLIENT_IDS`).      |
| `EXPO_PUBLIC_BRANDED_ASSETS`       | on                          | bundle   | `false` never shows official crests, kits or photos (App Store builds).  |
| `EXPO_PUBLIC_SHOW_PROJECTIONS`     | off                         | bundle   | `true` shows Expected points and win chances (hidden for now; ADR 0014). |

The app name and colours come from `apps/app/brand.json`.

## Simulator on mocks

No server. The mock world lives in memory and resets on every launch; any
6-digit code except `000000` signs in.

```bash
npm run test:ios -- --build smoke   # builds + installs the Release mock app, runs one flow
```

or, with Metro and fast refresh (Debug build, dev client):

```bash
npm run dev:ios:mocks
```

## Simulator against the local API

The demo world from `npm run dev:stack` (Postgres in Docker, demo seed, the
API with dev magic links and the poller on the demo source; it never calls
FPL). Port 8080 taken? Use `HTTP_ADDR=:8090` and the matching URL below.

```bash
npm run dev:stack > /tmp/mfp-api.log 2>&1 &          # or in its own terminal
cd apps/app
npx expo prebuild --platform ios                       # once
EXPO_PUBLIC_API_BASE_URL=http://localhost:8080 xcodebuild \
  -workspace ios/MyFantasyPrem.xcworkspace -scheme MyFantasyPrem \
  -configuration Release -destination 'platform=iOS Simulator,name=MFP iPhone' \
  -derivedDataPath ios/build -quiet build
xcrun simctl install booted ios/build/Build/Products/Release-iphonesimulator/MyFantasyPrem.app
xcrun simctl launch booted com.myfantasyprem.app.dev
```

`npm run test:ios -- --api --build` does the same build (see
[Native tests](#native-tests)). For Metro instead: `npm run dev:ios` reads
`apps/app/.env.development` (`http://localhost:8080`).

Sign in as `demo@myfantasyprem.test`: tap "Email me a sign-in link", then
type the 6-digit `code=` from the newest `dev magic link` line in the API
log. The Simulator shares the Mac's network, so `localhost` works there
(not on a phone).

The mock build and the API build share a bundle id: installing one
replaces the other.

## Your own iPhone (free Apple ID)

A free Apple ID gives you a "Personal Team" that can sign development
builds for your own devices. Limits: a build stops opening **7 days** after
it was signed (rebuild and run again from Xcode), at most 3 such apps per
device, no Sign in with Apple, no universal links, no push, no TestFlight.

What you have to do once, by hand:

1. **Xcode → Settings → Accounts → +** → Apple ID → sign in with your
   Apple ID. A "(Personal Team)" appears under it.
2. **On the iPhone:** Settings → Privacy & Security → **Developer Mode** →
   on, restart, confirm. Connect it to the Mac with a cable, unlock it and
   tap **Trust This Computer**. (After the first run, Xcode can also use it
   over Wi-Fi.)

Each build:

1. Generate the project for a free team (no Sign in with Apple; the plain
   HTTP host is for the Tailscale API below; skip it if you use mocks):

   ```bash
   cd apps/app
   APPLE_SIGN_IN=false APP_HTTP_HOSTS=tail1234.ts.net \
     npx expo prebuild --platform ios --clean
   ```

2. Say which API the bundle talks to. Xcode bundles the JavaScript itself,
   so put it in `apps/app/.env.local` (git-ignored; Expo reads it for every
   build, so delete it afterwards or it also applies to web builds):

   ```bash
   # apps/app/.env.local
   EXPO_PUBLIC_API_BASE_URL=http://mac.tail1234.ts.net:8090
   ```

   For a phone build on mocks instead, write `EXPO_PUBLIC_USE_MOCKS=true`.

3. `open ios/MyFantasyPrem.xcworkspace` (the workspace, not the project).
4. In Xcode: select the **MyFantasyPrem** project → target
   **MyFantasyPrem** → **Signing & Capabilities** → tick **Automatically
   manage signing** → **Team: <your name> (Personal Team)**.
   If it says the bundle id is not available, change **Bundle Identifier**
   to something only you use, e.g. `com.<yourname>.myfantasyprem.dev`
   (or prebuild again with `APP_BUNDLE_ID=...`).
5. **Product → Scheme → Edit Scheme… → Run → Build Configuration:
   Release.** Release embeds the JavaScript, so the app works away from the
   Mac; Debug needs Metro (`npx expo start` from `apps/app`) on the same
   network.
6. Pick the iPhone in the device menu at the top and press **Run** (⌘R).
7. First launch on the phone: Settings → General → **VPN & Device
   Management** → your Apple ID → **Trust**. Then open the app.

After 7 days the app no longer opens: connect the phone and press Run
again (steps 3 to 6; no prebuild needed unless a prebuild value changed).

## Phone against the Tailscale API

The API on the Mac is served on the tailnet at
`http://mac.tail1234.ts.net:8090`.

- The iPhone needs the **Tailscale** app, signed in to the same tailnet
  and connected. Check from Safari on the phone:
  `http://mac.tail1234.ts.net:8090/healthz`.
- iOS blocks plain HTTP (App Transport Security) to anything but local
  addresses. `APP_HTTP_HOSTS=tail1234.ts.net` at prebuild adds an
  exception for that domain and its subdomains; it is refused for an EAS
  `production` build. Without it every request fails with a network
  error.
- `EXPO_PUBLIC_API_BASE_URL` must be the full URL with the port (step 2
  above). `localhost` on a phone is the phone.
- Signing in by email needs a code: if that API runs with
  `AUTH_DEV_MAGIC_LINKS=true`, the code is in its log (`dev magic link`
  line); otherwise it is emailed. Links in emails open the web app, so type
  the code in the app.

With HTTPS later (for example `tailscale serve` with a certificate, or the
deployed API), drop `APP_HTTP_HOSTS` and use the `https://` URL.

## Over-the-air updates

JavaScript changes reach the installed app without a reinstall:
`expo-updates` in the app, the Go API serving the
[Expo Updates protocol](https://docs.expo.dev/technical-specs/expo-updates-1/)
from a folder on the Mac, and a publish script that writes to it. No Expo
account and no paid service; plain HTTP over Tailscale works.

- **On:** only in a build prebuilt with `APP_UPDATES_URL`. Without it
  (CI, tests, web, mock and simulator builds) the app never checks.
- **When:** the app asks on every launch, downloads a newer update in the
  background and runs it on the **next** launch; offline or with the Mac
  asleep it starts at once on the update it has. Account → **App version**
  shows the running update (or "Built-in version") and the runtime, and
  **Check for updates** fetches one now and offers **Restart to update**.
- **Which binaries:** an update carries a runtime version, by default a
  fingerprint of the native project (native dependencies, app config,
  config plugins, `apps/app/package.json` scripts). The server only hands
  an update to an app with the same runtime version, so JavaScript never
  lands on a binary it was not built for. No code signing.

### Build once with updates on

Put every prebuild value in `apps/app/.env.local`. Prebuild, Xcode's build
(which computes the fingerprint without your shell's variables) and the
publish script all read that file, so they agree on the runtime version:

```bash
# apps/app/.env.local
APPLE_SIGN_IN=false
APP_HTTP_HOSTS=tail1234.ts.net
APP_UPDATES_URL=http://mac.tail1234.ts.net:8090/updates/manifest
EXPO_PUBLIC_API_BASE_URL=http://mac.tail1234.ts.net:8090
```

Then, from `apps/app`, `npx expo prebuild --platform ios --clean` and steps
3 to 7 of [Your own iPhone](#your-own-iphone-free-apple-id) (Release). The
file also applies to web builds from this checkout: move it aside while
running `npm run build:web`, and put it back to publish.

### Publish an update

From the repo root, on the commit you want on the phone, with the same
`apps/app/.env.local`:

```bash
npm run updates:publish -- --dir ~/mfp-tailnet/updates      # --keep 5 by default
```

It exports the iOS bundle (`expo export --platform ios`), writes
`~/mfp-tailnet/updates/<runtime version>/<update id>/` and keeps the newest
five updates of that runtime version. It prints the runtime version: its
first eight characters must match Account → App version on the phone.
Then open the app twice (once to download, once to run it), or use
**Check for updates**.

If they do not match, the phone never gets the update: something native
differs between the build and this checkout. Rebuild from this checkout
(below), or, if you are sure nothing native changed, pin
`APP_RUNTIME_VERSION=<name>` in `.env.local` for both the build and every
publish (then change it yourself on every native change).

### What still needs a reinstall

- **Native changes:** a new or upgraded package with native code, an Expo
  SDK upgrade, anything in `app.config.ts` (name, icon, splash, plugins,
  Info.plist, entitlements) or a prebuild variable, and `apps/app/package.json`
  scripts. They change the runtime version: prebuild with `--clean` and
  run from Xcode again. Updates published for the old runtime do not
  apply to the new binary: publish again after installing it.
- **The 7-day signature** of a free Personal Team: the app stops opening
  after 7 days whatever its updates. Run it from Xcode again (no prebuild
  needed if nothing native changed); with the same `.env.local` it keeps the
  same runtime version and picks up published updates as before.

### Hosting (office manager)

The API serves updates when `UPDATES_DIR` is set: `GET /updates/manifest`
and `GET /updates/assets/...` on the same port as the API, public (the app
asks before anyone signs in), outside the `/v1` contract. Tailscale already
forwards `:8090` to it, and asset URLs use the host the phone asked (as the
realtime tickets do), so `static.mjs` and `tailscale serve` need no change.
Changes to `~/mfp-tailnet/run.sh`:

1. Rebuild the API from this branch, keeping the old binary:

   ```bash
   cp ~/mfp-tailnet/mfp-api ~/mfp-tailnet/mfp-api.v11-backup
   (cd server && go build -o ~/mfp-tailnet/mfp-api ./cmd/api)
   mkdir -p ~/mfp-tailnet/updates
   ```

2. In `run.sh`, add `UPDATES_DIR="$D/updates"` to the API's environment
   (next to `ASSETS_CACHE_DIR="$D/assets-cache"`), then restart `run.sh`.
   The API log says `over-the-air app updates are served from /updates/`.
3. Check from the Mac after a first publish (the URLs in the answer must
   start with `http://mac.tail1234.ts.net:8090/`):

   ```bash
   RT=$(ls ~/mfp-tailnet/updates | head -1)
   curl -s -H 'expo-protocol-version: 1' -H 'expo-platform: ios' \
     -H "expo-runtime-version: $RT" \
     http://mac.tail1234.ts.net:8090/updates/manifest | head -c 600
   ```

`~/mfp-tailnet/updates` needs no backup: publishing again rebuilds it.

## TestFlight (later)

Needs the paid **Apple Developer Program** ($99 a year) on the owner's
Apple ID. Then:

1. **App Store Connect** (appstoreconnect.apple.com) → My Apps → **+** →
   New App: platform iOS, the store name, the final bundle id (register it
   under Certificates, Identifiers & Profiles → Identifiers, with Sign in
   with Apple enabled, and associated domains if universal links ship).
2. Link EAS once: `npx eas-cli login` and `npx eas-cli init` from
   `apps/app` (free Expo account). EAS creates and stores the distribution
   certificate and provisioning profile when you sign in with the paid
   Apple ID during the first build; do not reuse anyone else's.
3. Set the store values as EAS environment variables (production):
   `APP_BUNDLE_ID`, `EXPO_PUBLIC_API_BASE_URL` (HTTPS; `app.config.ts`
   fails the build without it), and `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` if
   Google sign-in ships. The `production` profile in `eas.json` sets
   `EXPO_PUBLIC_BRANDED_ASSETS=false`: no official crests, kits or photos
   in a store build (Apple's intellectual-property guideline), whatever the
   server's `BRANDED_ASSETS`. The server needs the bundle id in
   `APPLE_CLIENT_IDS` (and the iOS client id in `GOOGLE_CLIENT_IDS`).
4. Build and upload:

   ```bash
   cd apps/app
   npx eas-cli build --platform ios --profile production
   npx eas-cli submit --platform ios --latest
   ```

5. App Store Connect → TestFlight: add testers (internal testers need no
   review; external ones need a short beta review). Export compliance is
   answered in `app.config.ts` (`usesNonExemptEncryption: false`).

The store listing carries the legal notice and the privacy details
(`app.config.ts` declares the privacy manifest: email and user id, for app
functionality, no tracking).

EAS profiles (`apps/app/eas.json`): `development` (simulator, dev client,
mocks), `development-device` (same for a device; needs a paid team on
EAS), `preview` (internal, mocks), `production` (store).

## Native tests

The Maestro flows run against a Release build on a booted simulator. Not in
`.office/checks` (they need macOS, Xcode and Maestro).

```bash
npm run test:ios -- --build          # build + install the mock app, run every flow
npm run test:ios                     # rerun on the installed build
npm run test:ios -- tour             # one flow (e2e/ios/flows/tour.yaml)
npm run test:ios -- --screenshots    # also refresh docs/screenshots/ios
IOS_DEVICE=<udid> npm run test:ios   # a given simulator (default: the booted one)
```

On mocks (`e2e/ios/flows`):

- `smoke`: sign in by code, the join sheet over the keyboard, a points
  breakdown sheet, a keeper swap, a player card swiped away, a draft pick.
- `tour`: every screen by deep link, with a screenshot each.
- `links`: a claim link opened signed out, and an emailed sign-in link that
  waits for Continue.
- `nav`: the league's top tabs swiped left and right (the selected tab
  checked after each swipe) and tapped, a horizontal row inside a page that
  scrolls instead of paging, and every section of the bottom bar.
- `sheets`: the full-height player card closed by a pull down and by its
  one floating ✕ (`sheet-close`, checked to be the only one), the club
  pop-up (a centred dialog) closed by a tap on its backdrop, the Players list
  (FlashList) flung to its end and back with rows on screen at every stop,
  and the saved query cache: a keeper swap, then a relaunch that shows the
  swapped lineup (the mock world is rebuilt on launch, so only the cache
  has it) and, once that entry is stale, a relaunch that refetches the
  rebuilt world. Screenshots in `docs/screenshots/ios-wave-b`.
- `freeze`: the owner's frozen app after a sheet closed around a
  mutation. Five times: a player card from Status, the Avoid tag set and
  removed, closed by ✕ and by a pull down, each followed by a tab switch
  that must land. Then the swap dialog on Team opened, closed, opened again
  and closed by a tap on its backdrop, a saved swap, and tab switches. (The native mock build
  has no scenarios, so a server-refused save is covered by the web test
  `e2e/swap-freeze.spec.ts`.)
- `card-pull`: the full-height player card scrolled a little and back to
  the top, then pulled down once from its tag chips (not the grabber). It
  must close on that first pull, five times in a row.

Against the local API (`e2e/ios/api-flows`), on a fresh demo database:

```bash
HTTP_ADDR=:8080 npm run dev:stack > /tmp/mfp-api.log 2>&1 &
API_URL=http://localhost:8080 API_LOG=/tmp/mfp-api.log npm run test:ios -- --api --build
```

`walkthrough` signs in as the demo user with the code from the API log
(the script serves it to Maestro from `API_LOG`), then Status, Team (a
swap), Players and a player card, a waiver claim (a free-agent pickup in
the day before a deadline, when the demo world has nobody on waivers), a
trade offer, Activity (from League)
and the draft room of a league it creates (the demo leagues are past their
drafts, and the room's link only shows before and during one). It changes
the demo data, so run it on a freshly seeded database: `docker compose
down -v` (drops the local demo database) and `npm run dev:stack` again.

The script pre-approves the app's URL scheme on the simulator: otherwise
iOS asks "Open in MyFantasyPrem?" on every deep link, a system alert
Maestro cannot tap.
